# GeoCheck AI — Продуктовый бриф

## Цель

Построить модуль **GeoCheck AI**: автоматическая проверка соответствия растрового чертежа **всем условиям геометрической задачи** (текст задачи → правила → верификация чертежа). Задачу мы **не решаем** — только проверяем корректность построенного чертежа. Школьный/портфолио проект: чистый код, тесты и аккуратный README важнее масштаба.

Единый источник правды — ТЗ в корне репозитория (`product-brief.md`). Этот файл — его агент-читаемая адаптация.

## KPI (из ТЗ)

- **Accuracy** ≥ 95% на цифровых чертежах.
- **Автоматизация:** полное исключение ручной проверки графической части преподавателем.
- (Требование «≤ 3 с на CPU» из ТЗ **убрано**; даунскейл и замер стадий остаются как инженерные практики, не как контракт.)

## Область (сквозной пайплайн, ТЗ §2)

1. **Вход:** растровое изображение чертежа + **строка текста задачи** (свободный текст, НЕ выбор правила из списка).
2. **Экстракция линий:** поиск всех отрезков с определением их экранных координат (min длина 30 px).
3. **Дедупликация:** кластеризация (разность углов ≤ 5° и евклидово расстояние ≤ 7 px) + слияние кластера по двум самым удалённым точкам.
4. **OCR:** одиночные латинские буквы (A–Z), автоприведение к UPPERCASE, сохранение координат центра.
5. **Сборка графа:** вершина = точка пересечения отфильтрованных отрезков; буква привязывается к ближайшей вершине ≤ 40 px.
6. **Анализ текста задачи → правила:** перевести текст задачи на «язык правил» программы. **Основной путь — детерминированный оффлайн-парсер** (чистая функция); **фолбэк — LLM API (Gemini)** с жёстким промптом, ответ строго в JSON (формат правил — `architecture.md`, «Rule-JSON»). Фолбэк включается пользователем вручную, **только если** он видит, что парсер не справился.
7. **Подтверждение правил пользователем (human-in-the-loop шлюз):** извлечённые правила показываются в UI человекочитаемым списком; верификация запускается только после явного подтверждения пользователем. Найдены неверные правила → пользователь вводит Google API key → Gemini дорабатывает извлечение → список обновляется → снова подтверждение.
8. **Верификация:** проверка чертежа по **всем** подтверждённым правилам (формулы в `architecture.md`), ε по умолчанию 3.0.
9. **Выход:** вердикт «Верно / Ошибка с описанием отклонения» (чеклист результатов по каждому правилу + общий итог).

## Типы правил (математический движок, ТЗ §3.3)

Система ищет в тексте задачи **все** применимые сценарии построения и проверяет только найденные, с настраиваемой погрешностью ε (по умолчанию 3.0). Базовые 4 + 4 новых (из ТЗ):

- **Градусная мера угла (ABC = N°):** |угол на рисунке − N| ≤ ε. Обобщает перпендикулярность (N = 90).
- **Параллельность (AB ∥ CD):** нормализованный угол между прямыми ≤ ε.
- **Равенство отрезков (AB = CD):** |L_AB − L_CD| ≤ ε px.
- **Принадлежность точки (M ∈ AB):** (AM + MB) − AB ≤ ε px (M строго между A и B).
- **Медиана (BK к стороне AC):** K — середина AC → `on-segment(K, AC)` + `equal(AK, KC)`.
- **Биссектриса (BM угла ABC):** |∠ABM − ∠MBC| ≤ ε (луч BM делит угол пополам).
- **Высота (BM к стороне AC):** BM ⊥ AC + M на прямой AC.
- **Перпендикулярность (ABC = 90°):** частный случай градусной меры; сохраняется как отдельный сценарий.

**Ограничение по постановке:** абсолютные длины из текста («АС = 16 см») **не верифицируются** — у растра нет соответствия «см → px». Верифицируются только структурные отношения и градусные меры. Длины из текста парсер извлекает (и показывает в списке правил) как «дано», без проверки.

## Нефункциональные требования и UX (ТЗ §4)

- **Отказоустойчивость:** ненайденная буква → мягкая ошибка `[Status: Error] Точка X не найдена на чертеже` (без падений/KeyError).
- **UI:** поле загрузки файла (Drag-and-Drop), **поле текста задачи** (вместо выпадающего списка правил), ползунок ε, область предпросмотра правил с подтверждением, опциональное поле Google API key (фолбэк).
- **Секреты:** API key вводится пользователем в UI по требованию (fallback-сценарий); **в репозитории и `.env` ключей нет** (решение зафиксировано 2026-09-17).

## Что такое хороший результат (критерии приёмки, ТЗ §5 + testdata)

- **testdata-корпус (`testdata/`):** `<номер задачи>-text.txt` + `<номер задачи>-photo...[-(N)]?-<true|false>.jpg`. Связка «текст + картинка» должна давать вердикт, совпадающий с суффиксом `true/false`. **Обе testdata-задачи обязаны парситься оффлайн-парсером** (без Gemini) — это acceptance-критерий парсера.
- Идеальный прямоугольный треугольник с подтверждённым углом 90° → `Success`.
- Угол 84° при ε=3 → `Fail` и текст: «Ошибка: Угол на рисунке равен 84.12°, отклонение составляет 5.88°» (контракт строки обновлён: **без имени угла**).
- Точка X на прямой отрезка, но вне отрезка → `Fail`.
- `pnpm test` + `pnpm typecheck` + `pnpm build` — зелёные; README честно описывает возможности.

## Подводные камни (обнаружено при приёмке testdata)

- В текстах задач **кириллические омоглифы** («АВС», «ВМ», «ВК») — нормализация А→A, В→B, С→C, К→K, М→M, Н→H, Е→E, О→O, Р→P, Т→T, Х→X **до** парсинга и сопоставления с OCR-метками.
- «true»-чертёж задачи 1 **не содержит** текстовой пометки угла 100° — градусная мера проверяется по геометрии изображения, а не по подписи на чертеже.
