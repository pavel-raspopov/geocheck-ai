# Plan: Текст задачи → правила → мульти-верификация чертежа (Phase 6, ТЗ ред. 2026-09-17)

**Дата:** 2026-09-17 · **Статус:** approved (plan mode, пользователь подтвердил flow) · **Execution:** inline (act mode, план одобрен — writing-plans handoff choice пропускается по наблюдению №3)

## Проблема

ТЗ изменилось: вход = изображение + **текст задачи** (свободный текст). Правила извлекаются из текста; верифицируются **все** найденные правила. Задача не решается — проверяется только чертёж. Добавлен acceptance-корпус `testdata/`.

## Зафиксированные решения (пользователь, 2026-09-17)

1. **Основной путь — детерминированный оффлайн-парсер** (без ИИ). Пользователь видит распознанные правила в UI.
2. **Если правила верны** → пользователь подтверждает → верификация. **Gemini не нужен.**
3. **Если парсер не справился** → появляется поле Google API key → Gemini дорабатывает извлечение → правила показываются → пользователь подтверждает → верификация.
4. **Human-in-the-loop шлюз обязателен:** верификация никогда не запускается по неподтверждённым правилам.
5. **Дефолтного ключа в `.env` нет** (в браузерном SPA `VITE_*` = публичный ключ в бандле). Key только через UI-поле (максимум localStorage), никогда в git.
6. Абсолютные длины («АС = 16 см») не верифицируются (нет масштаба см→px) — извлекаются как «дано».

## Контракт правил (Rule-JSON)

Расширяет пример ТЗ `{"points": [...], "relations": [["AB","CD","parallel"], ["ABC", 90]]}` tagged-вариантом (типы — `context/architecture.md`):

```
{kind:'angle', angle:'ABC', degrees:N}      // градусная мера (N=90 — перпендикуляр)
{kind:'parallel', a:'AB', b:'CD'}
{kind:'equal', a:'AB', b:'CD'}
{kind:'on-segment', point:'M', segment:'AB'}
{kind:'median', cevian:'BK', side:'AC'}     // → on-segment(K,AC) + equal(AK,KC)
{kind:'bisector', cevian:'BM', angle:'ABC'} // → |∠ABM − ∠MBC| ≤ ε
{kind:'height', cevian:'BM', side:'AC'}     // → BM⊥AC + основание на прямой AC
```

Парсинг: нормализация омоглифов (А→A, В→B, С→C, К→K, М→M, Н→H, Е→E, О→O, Р→P, Т→T, Х→X; `<`→`∠`) обязательна ДО разбора.

- **Парсер без ИИ:** обе testdata-задачи парсятся оффлайн (юнит-тесты читают `testdata/N-text.txt`).
- ТЗ §5: прямоугольный треугольник → Success; 84° при ε=3 → Fail `Ошибка: Угол на рисунке равен 84.12°, отклонение составляет 5.88°`; точка вне отрезка на прямой → Fail.
- Гейты: `pnpm test` + `pnpm typecheck` + `pnpm lint` + `pnpm build` + live QA.

## Шаги (TDD, один коммит на фичу)

- `src/pipeline/rules/types.ts` (`Segment`, `AngleName`, `Relation`, `ParsedTask`), `normalize.ts` (омоглифы), `parse.ts` (`parseTask`), спеки.
- Тесты: омоглифы, обе testdata-задачи (медиана+биссектриса+углы+«дано»), негативы (пусто → мягкая ошибка), детерминизм.
- Verify: `pnpm test` зелёный, parseTask(1-text) содержит median(BK,AC)+bisector(BM,ABC)+angle(ABC,100).

### 09 — Rule engine v2 (`rules-engine.ts`)
- Оценка `Relation[]` по графу; переиспользование формул `verify.ts` (угловая геометрия выносится в хелперы).

- Тесты: каждый kind (pass/fail/soft-error), агрегация, границы (M за B → Fail).

### 11 — UI v2 (mock-first)
- Mock: `src/mock/demo-task.ts` (пример правил). Компоненты: `task-text`, `rules-preview` (список + «дано» + «Подтвердить и проверить»), `gemini-fallback` (скрытая секция, поле key). Verdict-чеклист.

### 12 — testdata-харнесс

### 13 — Live QA + доки

## Риски

- **OCR на реальных сканах** (2-photo-true — шумный скан; 1-photo(1/2) — фиолетовые заливки угла, дуги, засечки): конкурирующие дуги могут дать лишние отрезки/вершины; калибровка констант или прегифт. Пороги — только через `constants.ts`.
- **ε=3.0 px для равенства** жёсткий для «фотографий» — если testdata не проходит, обсудить с пользователем калибровку (ТЗ фиксирует ε как настройку, не пороги дедупа).
- **LLM нестабилен** — потому парсер основной; Gemini-тесты только на записанных ответах.
