# 📋 ТЗ: Модуль верификации геометрических чертежей «GeoCheck AI»

## 1. Бизнес-цели и KPI

- **Цель:** Автоматическая проверка соответствия растрового чертежа текстовым геометрическим условиям задачи.
- **Accuracy (Точность):** >= 95% на цифровых чертежах.
- **Автоматизация:** Полное исключение ручной проверки графической части преподавателем.

## 2. Сквозной бизнес-процесс (Pipeline)

1. **Вход:** Растровое изображение чертежа + Строка геометрического условия задачи
2. **Экстракция линий:** Поиск всех отрезков с определением их экранных координат.
3. **Дедупликация (Фильтрация):** Объединение пиксельных дубликатов линий, вызванных их толщиной.
4. **Распознавание меток (OCR):** Поиск латинских букв вершин и координат их центров.
5. **Сборка графа:** Привязка распознанных букв к физическим точкам пересечения отрезков.
6. Анализ текста строки геометрического условия. Перевести текст задачи на язык понятных программе правил.
Использовать API больших языковых моделей (например, Gemini API Key), дав ей жесткий промпт: «Выдели из текста геометрические сущности. Выведи ответ строго в формате JSON: {"points": ["A", "B", "C"], "relations": [["AB", "CD", "parallel"], ["ABC", 90]]}».
7. **Верификация:** Проверка геометрического чертежа по формулам аналитической геометрии и соответствия условиям геометрической задачи.
8. **Выход:** Финальный UX/UI вердикт (Верно / Ошибка с описанием отклонения).

## 3. Функциональные требования и Бизнес-логика

### 3.1. Компьютерное зрение и OCR

- **Детекция линий:** Поиск отрезков любой ориентации. Минимальная длина отрезка для анализа — 30 пикселей.
- **Распознавание текста:** Строго одиночные латинские буквы (A-Z). Автоприведение к UPPERCASE. Сохранение координат центра буквы.

### 3.2. Алгоритмы фильтрации и сборки графа

- **Кластеризация линий:** Группировка отрезков в один класс, если разность их углов <= 5° и евклидово расстояние между ними <= 7 пикселей.
- **Слияние линий:** Финальный отрезок кластера строится по двум самым удаленным точкам внутри группы.
- **Связывание «Буква ➔ Вершина»:** Вершиной считается точка пересечения отфильтрованных отрезков. Буква привязывается к вершине, если расстояние до нее минимально и не превышает 40 пикселей.

### 3.3. Бизнес-правила Математического движка

Система должна искать в строке геометрического условия все возможные геометрические сценарии (правила построения чертежа) и проверять только те, которые нашла с настраиваемой погрешностью (по умолчанию epsilon = 3.0). Для примера, базовые геометрические сценарии:

- **Перпендикулярность (Угол в строке геометрического условия = 90°):** Нахождение угла через арккосинус отношения скалярного произведения векторов $\vec{1}$ и $\vec{2}$ к их длинам. Отклонение от 90° должно быть <= $\epsilon$.
- **Параллельность (1 отрезок || 2 отрезку из строки геометрического условия):** Модуль косого (псевдоскалярного) произведения векторов $\vec{1}$ и $\vec{2}$ должен стремиться к 0 (нормализованный угол между ними <= $\epsilon$).
- **Равенство отрезков (1 отрезок = 2 отрезку из геометрического условия):** Прямое сравнение евклидовых длин векторов. Разница $|L_{1} - L_{2}| <= \epsilon$ пикселей.
- **Принадлежность точки из строки геометрического условия отрезку :** Проверка через неравенство треугольника: $(13 + 32) - 12 <= \epsilon$ пикселей. Гарантирует, что точка 3 лежит на прямой строго *между точками* 1 и 2.
- Медиана (отрезок, соединяющий вершину с серединой противоположной стороны): проверять равенство отрезков на противоположной стороне.
- Биссектриса (отрезок луча, который делит угол пополам): проверять равенство углов, полученных делением угла биссектрисой.
- Градусная мера: проверять величину угла на соответствие своей градусной мере.
- Высота (отрезок перпендикуляра,выходящий из вершины, к противоположной стороне): проверить перпендикулярность прямых.

## 4. Нефункциональные требования и UX/UI

- **Отказоустойчивость:** Если ИИ не распознал запрашиваемую пользователем букву, система возвращает мягкую ошибку: `[Status: Error] Точка X не найдена на чертеже`, исключая падение бэкенда (`KeyError`).
- **Элементы управления UI:** Поле загрузки файла, поле загрузки текста с геометрическим условием задачи, ползунок (Slider) регулировки погрешности $\epsilon$.

## 5. Критерии приемки (Acceptance Criteria)

- **Успешный тест:** Для идеального прямоугольного треугольника с подтвержденным углом в 90° верификатор выдает статус `Success`
- **Тест на ошибку:** Если на чертеже угол равен 84° при заданном пороге погрешности в 3°, система возвращает `Fail` и текст: *«Ошибка: Угол на рисунке равен 84.12°, отклонение составляет 5.88°»*.
- **Тест на границы:** Если точка $Х$ лежит на одной прямой с отрезком $1$, но находится вне отрезка (за точкой отрезка $1$), движок обязан выдать статус `Fail`.

## 6. Дополнение проекта (решения команды GeoCheck AI — аддендум к ТЗ, зафиксирован 2026-09-17)

> Этот раздел — **не** часть оригинального ТЗ, а зафиксированные интерпретации и дополнения команды проекта, согласованные с заказчиком 2026-09-17. Оригинальные пункты ТЗ выше не пересматриваются. Детали реализации и план — `context/architecture.md` и `docs/superpowers/plans/2026-09-17-task-rules-verification.md`.

### 6.1. Пайплайн text→rules (уточнение §2.6)

- **Основной путь — детерминированный оффлайн-парсер** (чистая функция, TDD, без сети и ИИ). LLM API (Gemini) — **только ручной фолбэк**: включается пользователем, если он видит, что парсер не справился.
- **Human-in-the-loop шлюз (обязателен):** извлечённые правила показываются в UI человекочитаемым списком; верификация запускается **только после явного подтверждения правил пользователем** — как для парсера, так и для Gemini.
- **Fallback-сценарий:** пользователь открывает секцию фолбэка → вводит Google API key в UI-поле → Gemini дорабатывает извлечение → правила показываются → пользователь подтверждает → верификация.

### 6.2. Ключи и секреты

- **Дефолтного ключа в `.env` НЕТ** (в браузерном SPA `VITE_*` встраивается в бандл = публичный ключ). Google API key вводится пользователем только в UI-поле фолбэка (максимум localStorage); в репозитории ключей нет.

### 6.3. Границы верификации (уточнение §3.3)

- **Задачу не решаем** — проверяется только корректность построенного чертежа.
- **Абсолютные длины из текста («АС = 16 см») не верифицируются** — у растра нет соответствия «см → px». Извлекаются как «дано» и показываются в UI без проверки.
- Формализация сценариев (единый JSON-контракт правил, расширяющий пример §2.6): `angle {∠, N°}` (градусная мера; N = 90 — перпендикулярность), `parallel`, `equal`, `on-segment`, `median` (= принадлежность середины + равенство половин стороны), `bisector` (= |∠ABM − ∠MBC| ≤ ε), `height` (= ⊥ + основание на прямой). Полная таблица формул — `context/architecture.md`.

### 6.4. Приёмочный корпус (дополнение к §5)

- **`testdata/`** — acceptance-корпус: `<N>-text.txt` (текст задачи) + `<N>-photo[-(K)]?-<true|false>.jpg` (чертёж; суффикс = ожидаемый вердикт). Связка должна давать вердикт, совпадающий с суффиксом.
- **Обе testdata-задачи обязаны парситься оффлайн-парсером без ИИ** (acceptance-критерий парсера — иначе автоматический прогон невозможен без ключа).
- В текстах задач — **кириллические омоглифы** («АВС», «ВМ», `<АВС=84°`): перед парсингом обязательна нормализация А→A, В→B, С→C, К→K, М→M, Н→H, Е→E, О→O, Р→P, Т→T, Х→X; `<` → `∠`.

- Требование «≤ 3 секунд на CPU» из ТЗ убрано (ред. 2026-09-17); даунскейл изображения и замер стадий остаются как инженерные практики.
